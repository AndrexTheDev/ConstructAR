# Testing ConstructAR

Everything in this document has run. Nothing in it is a plan.

The app is verified in seven layers. Each one answers a question the others cannot, and each one
is cheap enough to run on every change — which is the only property that matters, because a test
that is too expensive to run is a document, not a test.

## Running it locally

```bash
python3 scripts/verify_sources.py --verbose          # layer 1, no JDK needed
python3 tools/build_site.py && python3 tools/seo_audit.py --verbose   # layer 2
gradle assembleDebug testDebugUnitTest               # layers 3 and 5
./tools/verify-native.sh                             # layer 4, no NDK needed
./tools/verify-native.sh --tsan                      # layer 4 under ThreadSanitizer
```

## What no automated layer can prove

There is no screenshot matrix. It existed during the beta test to answer *"does this screen fit in
Polish?"* without a device farm, and it was deleted when the review ended: its artifacts were never
verifiable from inside the pipeline, so keeping a green job that renders pixels nobody looks at
would have been the illusion of coverage rather than coverage. **Layout and touch behaviour are
checked with a phone in a hand** (`docs/RELEASE_CHECKLIST.md`), and the six locales are held to
their strings by the gates in layer 1 - the string that exists, is translated, and is measured
against its own formatting rules, not the pixels around it.

What *is* asserted about the landing pages is structural and lives in `tools/seo_audit.py`: every
page has exactly one `<h1>` and a description, no image is missing `alt`, every internal link and
fragment resolves, and the six locales carry the same metadata. That is a gate a person can read and
argue with; a golden image is not.

## What is *not* verified

* **ARCore on a device.** No emulator and no physical phone are part of this repository. The AR
  pipeline is unit-tested at the seam (`SurfaceHitResolver`, `HitStabilizer`, `RouteSession`,
  `MetricDepthCalibrator`) and never end-to-end. Nothing here claims otherwise.
* **The measurement claim.** ±2 cm on a detected wall between 1 and 4 m is a design target from
  the accuracy table; `docs/RELEASE_CHECKLIST.md` lists the laser-measure comparison that has to
  happen on real hardware before it can be called measured.
* **The PDF and the GLB on a device.** Both writers are pure Kotlin and are unit-tested for
  structure, but `PdfDocument` is an Android class: the file is produced, never opened, in CI.
* **Anything about a real purchase.** There is no checkout server; the licence flow is tested
  with keys minted by `tools/mint_licence.py`.

## Swept clean

Areas walked end-to-end with **no defect found**, so the next round does not spend its time there
again. Each line names what was read, not what was assumed.

* **AR screen re-entry and anchor lifetime.** `ArMeasureController.release()` runs from the
  screen's `DisposableEffect`, drops every anchor (`ArCoreAnchorFactory.detachAll`), closes the
  monocular depth model and stops the pipeline; `RouteSession` gets a fresh state per entry. No
  path found that leaves anchors or a depth session behind across entries.
* **PLY number formatting.** Every float goes through `String.format(Locale.ROOT, "%.5f", …)` and a
  non-finite value becomes `0.00000`, so a German phone cannot write a comma decimal into an ASCII
  PLY. The comment sanitising is finding 17's.
* **Export file names.** Two rooms exported in the same minute differ by name *and* timestamp in
  the stem, and `createFile` uniquifies a duplicate anyway, so nothing is silently overwritten.
* **A folder deleted after an export.** The app asks for the folder on every export and stores no
  handle, so a deleted folder cannot become a stale permission that fails later.
* **Project creation entry points.** The plan gate lives in `ProjectViewModel.createProject`, the
  only function that inserts a project, so a share intent or a future screen cannot bypass it.
* **Stale mesh export after a licence lapses.** `includeGlb`/`includePly` are `remember`ed *keyed on*
  `entitlements.isPro`, so a lapse resets them to the (false) entitlement rather than leaving a
  paid format ticked.
* **Storage reclaimed on delete.** `ProjectRepository.delete` removes the room's JSON, its draft and
  every photo whose name starts with `<id>__`, and the diary/defect delete paths remove their own
  photo, so deleting a room or one of its lines never leaves an orphaned image behind.
* **The last camera in a `remember`, round 77.** Finding 137 was fixed in the field book and the machinery that came out of it - three saved strings, one decision function, one deletion rule - was never carried to the project screen, which shoots the single photo the protocol opens with. A screen that has just been measuring with AR is exactly the one Android reclaims to make room for the camera, which is what makes the window real. What was wrong here is finding 186.
* **The fourth part of the draft, round 76.** The field book had been taught to survive recreation twice - the typed diary line and the typed defect title - and the three-way severity chip sitting between those fields was still a plain `remember`. What made it a defect rather than an annoyance is that the chip is not shown for its own sake: it is written into the project file the moment the defect is added. What was wrong here is finding 185.
* **The denominator nobody printed, round 75.** The backup card had learned by finding 85 to count the rooms it could not copy, and had never learned the same lesson for the photos in the sentence below those rooms: the "N of M" that is supposed to tell the operator how much of the job is missing was given the number that made it. What was wrong here is finding 184.
* **The compile check that compiled against itself, round 74.** The RTAB-Map branch is compiled on every push against stub headers, and those headers had been written from the bridge: seven signatures disagreed with upstream, so the documented optional build could not have compiled while the job reported that it did. What was wrong here is finding 183.
* **Who frees the native volume, round 73.** The TSDF context was freed by whichever thread called `close()`, on a timer, while the scan worker could still be inside it; and the guard that was supposed to make every later call harmless could never fire, because nothing zeroed the handle. What was wrong here is finding 182.
* **The voxel fusion without its lock, round 72.** The TSDF integration is the one place in the project where several threads write the same array on purpose, and it did the read-modify-write of `sdf` and `weight` after the shard lock had already been released. ThreadSanitizer named the three lines; the suite stayed green throughout, which is the part worth remembering. What was wrong here is finding 181.
* **The clip row's unstated default, round 71.** The material screen's waste row was given a
  sentence naming its three trade defaults in round 42; the clip row below it still offered
  "the trade default" against 30/60/90/100 cm without saying that the default is 60 cm of cable,
  90 cm of pipe, 50 cm of duct — and 50 cm is not even a chip. What was wrong here is finding 180.
* **The complaint that could not be withdrawn, round 70.** `RouteSession.setSpec` swapped the
  conduit and left the preview — and therefore the drawn tube and the bend-radius verdict — on the
  old profile, while `recompute` fed its own derived warning back in as a sticky one. What was
  wrong here is finding 179.
* **The question marks in the mesh header, round 69.** The PLY header carries the operator's own
  run labels, and it was encoded as US-ASCII - which does not fail on `ü`, it writes `?`. Four of
  the six locales could not get a room name into the file. What was wrong here is finding 178.
* **The clamp that cut a character in half, round 68.** The two functions between the operator's
  typing and a fixed-width page: `PdfText.ellipsize` cut by UTF-16 unit, so a room name with an
  emoji in it could be cut between the two halves of it, and the lone surrogate reached
  `Canvas.drawText` as the replacement glyph. What was wrong here is finding 177.
* **The save that deleted the room, round 67.** `SafeFiles.writeAtomically` has a fallback for
  filesystems that refuse to rename over an existing file: it deleted the target and then renamed
  the temporary into place. A volume that refuses both moves - and the fallback only runs after
  the ordinary rename already failed - left the room with no file at all, on the one path that
  exists because saving was already going wrong. What was wrong here is finding 176.
* **The appendix re-read that never happened, round 66.** Two documents described the printed
  photos as a 1 200 px re-read of the stored files "one page at a time", while the appendix printed the
  thumbnails the screen already held. What was wrong here is finding 175.
* **The two sentences on one baseline, round 65.** The protocol's notes under the procurement
  table: one call threw away where the note ended, so the next note printed over it, and none of them
  could move to the next page. What was wrong here is finding 174.
* **The copy that allocated every half second, round 64.** One more frame-path allocation, one
  file further on: the monocular pass copied the depth plane with `copyOf()` twice a second while the
  class around it reused every other buffer it owned. What was wrong here is finding 173.
* **The plane the pool never held, round 63.** The capture class that exists so the render loop

* **The six fields in the HUD's state, round 62.** The state object every frame is copied into,

* **The field book, round 29.** The three lists and their paperwork were read together. Working time:

  by the record itself so a double tap on a wet screen cannot double the hours, the twelve-hour

  labour line exists exactly when there is something to multiply (finding 78), and a shift that runs

  the disk agreed (findings 93, 125). The protocol prints the time rows forward, the diary the way
  the job happened and every defect with its day, severity and status; the photo appendix spends its

* **The bill of materials and its counts, round 28.** `MaterialListBuilder` was read against
  `PolylineMetrics` and the three places that print it. Grouping is by `bomKey`
  (`kind|material|size|standoff`), so two cables of the same size but different material cannot melt
  into one order line; the line's `withWasteMeters` is the same `total × (1 + waste)` the per-run
  metric computes, so screen, CSV and protocol agree to the last digit; `bomKey` keeps the standoff,

  reported figure rather than being folded into the metre (finding 114). The screen shows net, waste
  and order length per line plus clips, couplings and bends, and the CSV and order list carry the
  same numbers split per article. What was wrong on this surface is finding 135.
* **The room list and the way back, round 27.** The navigation was read as one story from the list
  into a room and out again. `refresh()` reloads from disk and reports rooms it could not read as a
  count of their own rather than failing the list (finding 92's sibling); the project limit is
  enforced in the view model, not in the button, so no future entry point can create a second room

  "room" instead of the repository's English default. On a cold start `resumeLastProject()` opens

  says nothing, because a message about a room he cannot see is noise at start-up. The id is
  written only after a successful load ("a room that cannot be opened is not one to come back to"),
  deleting a room clears it (finding 93), a room destination reached without a room shows a
  sentence and pops instead of an empty screen, and the resume waits for the introduction to be
  finished so a first run cannot be skipped. What was wrong here is finding 134.
* **Help and onboarding, round 26.** The six languages were read against the code as well as
  against each other. A mechanical pass over every key — the numeric tokens, the `%` signs and the
  units — found **no** drift between `values/` and the five translations, and the help screen's
  accuracy claims match the protocol's own sentence (1–2 cm on a plane, 3–6 cm on depth, ~1 % on a
  diagonal) in every locale rather than only in English. The onboarding's three promises are each
